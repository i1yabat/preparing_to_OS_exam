# План реализации тренажёра

Порядок работ и проверки приведены в [tasks.md](tasks.md), критерии — в
[spec.md](spec.md). Базовый вариант делать без кеша, затем добавить Valkey,
не меняя пользовательские сценарии.

## 1. Основа и данные

- Создать проект `config` на Django 5.2 и приложение `quiz`. Подключить
  PostgreSQL через `psycopg`; параметры и секреты брать из окружения.
- Создать `Topic` (`name`, уникальный `slug`), `Question` (ссылка на `Topic`,
  `text`, `explanation`) и `Choice` (ссылка на `Question`, `text`,
  `is_correct`). Задать обратные связи `questions` и `choices`, удалять
  зависимые записи каскадно. Частичным уникальным ограничением запретить
  два правильных варианта у одного вопроса. Наличие ровно одного верного
  варианта проверить для каждого вопроса фикстуры.
- Создать начальную миграцию. Подготовить `quiz/fixtures/demo.json`: две
  темы `processes` и `memory`, 10 вопросов и 40 вариантов с пояснениями у
  вопросов. Загрузка — `manage.py loaddata demo.json` после миграций.

## 2. Маршруты и форма

| Маршрут | Ответ |
| --- | --- |
| `GET /` | Список тем: название, slug и число вопросов, включая ноль. Для подсчёта использовать `Count("questions")`, отсортировать по названию и ID. |
| `GET /topics/<slug>/` | Страница темы с формой. Вопросы и варианты показать в порядке ID; варианты загрузить заранее. Для пустой темы не показывать форму, неизвестный slug обрабатывать как 404. |
| `POST /topics/<slug>/` | Проверить ответы на сервере. При ошибках вернуть связанную форму; при корректной отправке показать балл и разбор. Неизвестная тема также возвращает 404. |

Формировать обязательное поле с радиокнопками для каждого вопроса и
допускать только идентификаторы его вариантов. Проверять пустые,
посторонние и повторные значения, отклонять поля для вопросов за пределами
темы. Отправку защитить CSRF. Для зачёта сравнить каждый проверенный
идентификатор с верным вариантом из базы, начислить 1 балл за совпадение и
вывести пояснения только к ошибкам. Не сохранять попытки.

## 3. Интерфейс

Вынести навигацию и подключение общего CSS в `base.html`. Сделать
`home.html` с карточками, `topic_detail.html` с отдельными группами
радиокнопок и видимыми ошибками полей, `topic_result.html` с крупным
баллом, правильными ответами и пояснениями. На небольших экранах
перестраивать карточки и кнопки в один столбец. Использовать нативные
элементы форм, видимый фокус и подписи, по которым можно нажимать.

## 4. Контейнеры и кеш

- В `compose.yaml` описать `web`, `db` и `valkey`. Хранить данные PostgreSQL
  в именованном томе. Настроить пробы `pg_isready` и `valkey-cli ping`;
  `web` должен ждать готовности обеих зависимостей. Наружу публиковать
  только `web` на `127.0.0.1:8001`. Valkey работает во внутренней сети и
  не хранит пользовательские данные на диске.
- Подключить штатный Django-бэкенд `RedisCache` с клиентом `redis-py` к
  `redis://valkey:6379/0`. На главной сначала читать ключ `quiz:topics`
  через Django Cache API. При промахе выполнить один запрос с агрегатом
  и сохранить список словарей с названием, slug и счётчиком на 60 секунд.
  Пустой список — сохранённое значение, а не промах. При попадании в кеш
  вернуть данные без обращения к ORM и не продлевать TTL.
- PostgreSQL остаётся источником данных. После изменения фикстуры
  допускается задержка обновления главной до истечения TTL или точечное
  удаление ключа. Страницы вопросов и результаты не кешировать.

## 5. Проверка и сдача

Запустить тесты моделей, страниц и валидации в Compose. Сравнить
холодный и прогретый запросы к главной на реальных PostgreSQL и Valkey:
показать ключ с TTL и посчитать запросы Django к базе. Пройти тест с
ошибками и пропуском, проверить мобильную вёрстку. В README оставить
воспроизводимые команды, в REPORT — фактические результаты.
